# Opportunity discovery

Research date: 2026-09-06. No paid sessions used. Scores, frequency, buyer interest, development time, and differentiation are judgments to test, not market measurements. Primary documentation establishes technical failure modes and existing capabilities; it does not establish demand.

## Recommendation

**Final recommendation under the Free-plan constraint: PatchProof**, described below. Parallel API research reports a paid entitlement requirement for desktops, so the initially preferred CSV desktop direction fails the current deployment gate. The cost formula alone does not establish entitlement. CSV remains a future option, not the proposed build.

The original conditional recommendation was **CSV Roundtrip Receipt**: prove what happens to a CSV when a named version of LibreOffice Calc imports, saves, and reopens it with explicitly recorded settings. Return cell-level original/observed differences, formula-versus-text status, an evidence screenshot, and reproducible inputs. Target developers shipping CSV exports to operations teams. Start with uploaded synthetic or non-sensitive files; a browser export integration is optional and should not be manufactured merely to exercise another API.

The distinction is consumer behavior, not CSV syntax validation. Microsoft documents leading-zero loss and a 15-significant-digit numeric ceiling; OWASP documents formula interpretation and warns that save/reopen can invalidate escaping strategies. Neither source permits claiming that a LibreOffice test certifies Excel compatibility. The first release must label the actual engine, version, locale, filter settings, and scope on every receipt. [Microsoft conversion behavior](https://support.microsoft.com/en-us/office/keeping-leading-zeros-and-large-numbers-1bf7b935-36e1-4985-842f-5dfa51f85fe7), [OWASP CSV injection](https://owasp.org/www-community/attacks/CSV_Injection).

Critical challenge: LibreOffice's documented command-line CSV filters already provide the execution primitive. A local container can do the same conversion. Solari contributes disposable preinstalled office desktops and visible evidence without installing office software; the product contributes a useful failure taxonomy, controlled experiments, and actionable differences. Without those, it is a thin conversion wrapper. [LibreOffice CSV filters](https://help.libreoffice.org/latest/en-US/text/shared/guide/csv_params.html), [Solari templates](https://docs.getsolari.com/templates).

## Primary evidence and competing solutions

- **CSV:** Microsoft documents automatic data conversion and explicit text-import controls. LibreOffice exposes delimiter, encoding, quoted-text handling, special-number detection, scientific notation, and formula-evaluation options. This makes settings part of the experiment, not implementation trivia. OWASP's warning concerns cross-application behavior, so a byte-level dangerous-prefix scanner alone cannot certify consumer safety. Use only harmless local arithmetic canaries, never network or command formulas. [Microsoft](https://support.microsoft.com/en-us/office/keeping-leading-zeros-and-large-numbers-1bf7b935-36e1-4985-842f-5dfa51f85fe7), [Calc](https://help.libreoffice.org/latest/en-US/text/shared/guide/csv_params.html), [OWASP](https://owasp.org/www-community/attacks/CSV_Injection).
- **Backup restore:** restic already restores snapshots and can verify restored file contents. SQLite exposes integrity checks. A new product must test application-level invariants after restoration; repeating a checksum adds little. Restrict the MVP to one supported app and synthetic backup, because arbitrary production backup support adds secrets, transfer, storage, and recovery complexity. [restic restore](https://restic.readthedocs.io/en/stable/050_restore.html), [SQLite integrity_check](https://www.sqlite.org/pragma.html#pragma_integrity_check).
- **Package consumer proof:** npm pack creates the distributable and supports dry-run reporting; npm install accepts tarballs. The product must actually consume the package outside the source tree, not merely list files. This is easy to reproduce in ordinary CI, limiting Solari differentiation. [npm pack](https://docs.npmjs.com/cli/v11/commands/npm-pack/), [npm install](https://docs.npmjs.com/cli/install/).
- **Quickstarts:** pytest already executes doctest examples; GitHub Actions already runs jobs in containers; Read the Docs already builds PR previews. The remaining gap is an explicit end-to-end newcomer scenario with a real artifact/response assertion. Natural-language README interpretation is unnecessary and unreliable for the MVP. [pytest](https://docs.pytest.org/en/stable/how-to/doctest.html), [GitHub container jobs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/run-jobs-in-a-container), [Read the Docs previews](https://docs.readthedocs.com/platform/latest/pull-requests.html).
- **Document rendering / reproducibility:** diffoscope already examines many binary formats and emits reports. Solari's office template includes LibreOffice and a PDF viewer; using it does not establish document correctness. New value must be domain assertions such as required invoice text/page count, not an existing diff wrapped in a dashboard. [diffoscope](https://diffoscope.org/), [office template](https://docs.getsolari.com/templates).
- **PDF conformance:** veraPDF already supplies formal validation and reports for PDF/A and machine-verifiable PDF/UA checks. Reject as primary product unless a specific institution has an unmet workflow. [veraPDF validation](https://docs.verapdf.org/validation/).
- **Downloads:** Playwright exposes download events and saveAs. A standalone remote download checker has almost no defensible product surface. [Playwright downloads](https://playwright.dev/docs/downloads).

## Shortlist under adversarial review

| Candidate | Why not local Playwright or an API? | Honest Solari advantage | Differentiation / defensibility / OSS potential | First real-use validation |
|---|---|---|---|---|
| CSV roundtrip | Playwright alone cannot execute Calc semantics; a local Calc CLI absolutely can | Disposable office environment, recorded version/settings, optional live desktop evidence | Small corpus of import pitfalls plus trustworthy cell-level receipts; defensibility initially weak, OSS contribution potential good | Run on an actual project's non-sensitive CSV export, obtain one reproducible changed cell and actionable fix |
| Restore drill | APIs/CLI can restore; browser only verifies the resulting app | Clean compute boundary for a destructive restore rehearsal with a hard TTL | App-specific restore assertions; defensibility from maintained adapters only after real use | One real open-source app's sample backup and published restore procedure, with deliberate missing-data negative control |
| Package consumer proof | Local shell and CI are sufficient | Run a proposed package in a clean remote machine without polluting contributor computer | Very weak moat; useful OSS release recipe but likely not standalone business | Real tarball outside checkout, intentional missing file, fail then pass |
| README quickstart proof | Container CI is sufficient; browser evidence alone is not a product | Disposable clean environment and hosted preview shared with reviewer | Stronger only if failure evidence maps to precise docs steps and reproducible commands; still high wrapper risk | Follow one upstream quickstart verbatim, prove an observable output, avoid inventing a planted-only demo |

CSV wins for a visible, understandable cross-boundary failure with a relatively small deterministic core. Restore drills are the stronger alternative on severity but need a sharply chosen application and more setup. Package and README proof are easier fallback projects, but require candid acknowledgment of existing CI substitutes.

### Added finalist: PatchProof (selected after desktop entitlement gate)

**Problem:** a candidate passes a test, but the reviewer has no evidence that the same test actually reproduces the reported bug on the baseline. Run a reviewer-supplied explicit reproducer against pinned baseline and candidate revisions in two sequential fresh sandboxes. Emit `reproduced-and-fixed` only when the baseline fails with the expected witness and the candidate completes the same assertion successfully. An install failure, timeout, missing test, or unrelated crash is inconclusive. Pytest's documented exit codes distinguish test failures from usage/internal/no-tests errors; a blanket nonzero→zero oracle is insufficient. [pytest exit codes](https://docs.pytest.org/en/stable/reference/exit-codes.html).

Score **4/4/4/4/4 = 20/25**, medium wrapper risk; practical first choice because it avoids paid desktop entitlement. User: OSS maintainer reviewing bug-fix contributions. Frequency: each suspicious bug fix, rather than every commit. Willingness to pay: low for individuals and unproven for teams. MVP: pinned public repo/revisions, one explicit setup command, identical external reproducer bytes, baseline/candidate expected witnesses, a bounded timeout, machine-readable receipt and readable logs. Planning estimate 1–2 days. Demo: real historical bug/fix with a tiny test, plus a negative control where setup fails and the result must be inconclusive.

**Why not local Playwright/API/CI?** Local shell and standard CI can perform this entire workflow. GitHub already restricts ordinary fork pull-request workflows to read-only tokens and withholds secrets; do not imply all CI exposes secrets. GitHub does warn against running untrusted code in privileged `pull_request_target` and `workflow_run` contexts. Solari's credible advantage is ad hoc contributor-code execution away from the maintainer's workstation, without Docker installation or repository workflow permissions, in disposable environments. It is a convenience and isolation boundary, not a unique security guarantee. [GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use), [GitHub fork workflow security](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

**Product value beyond a wrapper:** paired execution semantics; stable source/test/environment manifest; precise pass/fail/inconclusive states; evidence that names the assertion rather than just displaying red/green logs; a reproducible local command. Hashes bind files and logs to a receipt, but do not establish trustworthy execution or prevent hostile candidate code from printing a fake witness. Reviewer-owned tests and an explicit trust model are essential. Do not call the output an attestation, security audit, proof against malicious code, or mathematical proof of correctness.

**Defensibility / OSS / real use:** initial moat is weak and the algorithm is easy to copy. OSS usefulness can come from reusable minimal reproducers and clear evidence semantics. Do not build an adapter marketplace or AI test generator. Validate one actual upstream historical fix, then ask whether maintainers would use the CLI on a new incoming report; without that evidence this remains a credible internship artifact, not validated business demand.

## Budget and stop conditions

Solari currently lists Free browser time at $0.15/hour, compute at $0.0525/vCPU-hour plus $0.0165/GB-hour, and a $0.02/hour VM screen surcharge. Free has $3 monthly credits and one concurrent sandbox. A 1-vCPU/2-GB sandbox is therefore $0.0855/hour; a desktop at those resources would be $0.1055/hour. At that hypothetical size, a five-minute desktop is about $0.0088; actual default size, startup duration, and billing behavior must be measured before promising a cost. Do not assume the office desktop supports that minimum size. [Solari pricing](https://docs.getsolari.com/pricing).

Use one sequential session, a short server TTL, a client deadline, cleanup in finally, and a conservative per-run estimate. Develop parsing/diff/report logic locally; use at most a handful of real sessions for integration. No LLM, captcha, proxy, or autonomous exploration is needed. Reject a product that needs lengthy provisioning or persistent sessions just to demonstrate its core result.

Before committing to CSV: verify office template availability, programmatic file transfer, deterministic Calc filter/UNO behavior, and downloadable evidence. A screenshot is corroboration; typed cell results are the oracle. If an explicit import mode preserves all supplied fields, report that result rather than manufacturing corruption. If only headless conversion runs, call it a headless conversion test, not a human double-click simulation. If real export files reveal no meaningful issue and maintainers already solve this with a short script, stop rather than build a dashboard.
