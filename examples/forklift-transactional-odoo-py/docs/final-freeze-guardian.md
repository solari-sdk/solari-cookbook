# Final-freeze guardian and challenger card

## Method–object guardian

**Authoritative source:** the first two `forklift-solari` ledger events and the
user objective: perform a difficult real GUI business workflow transactionally,
survive repeated hidden cases and intentional faults, and accept zero invalid
states inside a precise boundary.

**Target capability:** allow a fallible visible-computer worker to propose a
real Odoo purchase-to-pay state while guaranteeing that only a semantically
valid, immutable state can become the retained result.

**Method contract:** precommit cases, faults, oracle, thresholds, resource cap,
and stop rules; separate development from sealed evidence; preserve every
failure; compare a matched simpler baseline; inspect a frozen state with a
fresh read-only auditor; never call same-builder evidence independent.

**Current work and intended decision:** 16 audited developmental trials and a
completed six-case digest-frozen development plan decide whether the mechanism
is ready to freeze for a fresh final campaign.

**Causal bridge:** disposable state sandbox plus visible worker → exact
candidate snapshot → fresh semantic audit → bound selector → durable template.
Every arrow now has live development evidence: an accepted snapshot was
promoted, booted as a new sandbox, and re-audited with an identical verdict.

**Method verdict: pass for final freeze.** Development is prospective and
failure-preserving; the campaign has 16 audits with zero false acceptance; the
matched self-report baseline falsely accepted three bad states; the runtime
claim now matches the one-candidate implementation; and the final campaign has
a fresh sealed seed, fixed budget, exact code/dependency hashes, and stop rules.

**Object verdict: pass.** The worker operates real Odoo 19 stock, purchasing,
accounting, and payment through a visible browser, the database—not narration—
decides, and durable promotion has been closed by boot-and-reaudit.

**Classification:** ready for sealed adversarial verification. This is not
independent replication because builder context and implementation are shared.

**Disproportion check:** the ledger and verifier now expose material failures
and bind evidence, but further custody machinery would be drift unless it
changes promotion, final-freeze, or external-use decisions.

**Recommendation:** execute the frozen one-candidate-per-trial final protocol
once, without tuning. Seek a separately custodied reimplementation only if an
independence claim becomes decision-relevant.

**Work to discard or quarantine:** remove the three-candidate portfolio claim
from the final protocol; keep earlier development artifacts historical. Do not
call builder-run or same-workspace checks independent replication.

**Resume condition:** satisfied. The first sealed package was retired unopened
after preflight found incomplete dependency hashing. A fresh v2 package may be
opened only after its complete local import closure, exact host dependencies,
sealed case files, resource cap, and retry rules verify.

## Alex Lens challenge

**Decision at stake:** freeze Forklift for its final competition evidence or
continue architecture work.

**Real function sought:** prevent a fallible GUI operator from making an
unverified business state authoritative without destroying useful throughput.

**Hidden assumptions:** safety needs three competing branches; snapshot discard
is equivalent to full rollback; a selector result proves the promotion API;
technical validation alone proves people need the product.

**Neglected analogy:** CI artifact promotion. A build runs in an isolated job,
is content-frozen, tested elsewhere, and only the exact tested artifact is
released. Mapping: Odoo state branch = build, candidate snapshot = artifact,
oracle = test suite, template promotion = release. Break point: CI usually has
no real business ledger and cannot undo external bank/email effects.

**Assumption inversions:**

1. If three branches are unnecessary, one disposable candidate plus a strict
   reject gate is cheaper and causally clearer. Development supports this.
2. If “rollback” means abandoning an isolated proposal rather than reversing
   arbitrary side effects, the boundary claim becomes stronger and more honest:
   internal snapshotted bytes only; external effects must remain staged.

**Strongest rival explanation:** Odoo's own constraints plus a strict SQL
postcheck catch errors; Solari contributes only disposable hosting. A matched
baseline must therefore show cases where the visible worker reports completion
and a mutable workflow would accept the result, while Forklift's isolated
semantic gate refuses it and preserves the canonical state.

**Better alternative:** keep the minimal one-candidate CI-style mechanism,
remove portfolio rhetoric, and make the product contract adapter-based:
`canonical snapshot + GUI task + semantic oracle -> durable tested template or
nothing`.

**Cheapest discriminating tests:** recompute the matched screen baseline from
the existing wrong-price and wrong-quantity trials; then exercise actual durable
promotion and boot/re-audit the promoted template.

**Recommendation:** revise, then proceed. Do not start over; the simpler
mechanism is already the working implementation.

**What would change this recommendation:** any invalid state selected, a
promoted template that differs from the audited snapshot, inability to boot the
promoted state, or evidence that a single mutable instance with matched checks
and resources preserves the same canonical safety.
